## Part B 设计要点

### B1 网关路由升级

- 调用面约定：各业务调用引擎时传 `app_key`（chat / money_parse / papers_translate / papers_qa / polish / embedding…），引擎查 model_assignments 解析主模型 + 备用链；
- `route_service.resolve_default()` 演进为 `resolve_for(app_key)`；未配置指派的应用回落默认路由（兼容期）；
- 兜底只管「首 token 前」的失败（流式开始输出后不可换模型——所有同类产品同限制）；
- 熔断：主模型连挂 N 次自动摘出旋转、备用顶上、探测恢复后自动切回（参数 N 与探测频率开工时定）；
- 记账：chat_once/chat_stream/embeddings 出口统一写 llm_call_logs（含 usage；mock 模式记 0 或跳过）；
- 对外 `/gw/v1` 不加指派概念（model 参数直查照旧），与内部 app_key 路由并行不悖。

### B2 Hatchet 流水线

- docker-compose 增 hatchet-engine 服务，PG 用现有实例独立库名；
- 论文域首批三条：每日抓取（替 /internal/jobs/papers-crawl 手动触发）、解析任务轮询、digest 推送；
- 幂等键落库（收编 Q11 进程内当日标记）；
- 管理页可查看运行状态（链接进 /admin/hatchet 子路径控制台）。

### B3 工程三小件

- 共享 httpx client：`app/services/http_client.py`，lifespan 建/销毁，网关/抓取/未来 MinerU、Unpaywall 共用；
- tenacity：装饰 NCBI esearch/efetch、Unpaywall、MinerU 提交/轮询、LLM 瞬时错误（替 papers_crawl.py:344 手写重试）；
- nh3：建统一渲染服务（markdown-it-py 渲染 → nh3 消毒），chat/论文预览/笔记共用；真前端前可先用于后端任何输出 HTML 的口子。

### B4 明确不做

- 不引入 LiteLLM/one-api/Portkey/Langfuse 任何服务（只抄设计，见《组件选型》第四部分）；
- 不上 Prefect/Airflow/Windmill；
- 不另开任何管理端口/Web；
- 统计不上 Prometheus/Grafana（PG 聚合查询即够）。

### 步 1：供应链基建

目标：把 D6/D13/D14 纪律落成机制。**本期不升级任何包、不改业务代码**，只盘点 + 锁定。

1. 盘点全部依赖：backend 的 requirements*.txt、docker-compose.yml 全部镜像。
2. 逐个直接依赖查安全公告：无未修高危 CVE → 锁当前稳定版；有 → 先出影响面评估（见「升级作业指导」），衡量后锁官方修复版（最安全版本原则）。
3. 建锁文件机制：requirements.in（人维护直接依赖）→ `uv pip compile --generate-hashes`（uv 不可用则 pip-tools 等价）→ requirements.txt（精确 `==` + 哈希）；安装一律 `pip install --require-hashes`。
4. docker-compose.yml 镜像全部 pin 固定 tag + digest（固定现状，不顺手升级）。
5. 验收：干净环境按 lockfile 装通 → pytest 全过 → ruff 过 → 后端真实启动冒烟 → commit（`chore(依赖)` 前缀）。

### 步 2 前置核验拍板回执（2026-10-25 19:15 需求会话裁定）

- digest 一致性：**通过**（锁定 `35caba83…` 与 Docker Hub 官方逐字符一致，国内镜像 serving 同 manifest）。
- **python:3.14-slim 44 个无修复高危 → 接受残余风险，不换基础镜像**：全生态无修复版（Debian 13 未出补丁、该 tag 已是最新 digest），换基础镜像属大动作且同系问题难免；暴露面不可达——非 root（UID 10001）+ 默认 capability 裁剪，util-linux 挂载/nsenter 类、libsystemd0、perl-base 等在本部署形态下不可利用。跟修走升级作业指导触发器（安全公告或 3 个月评估时重建镜像取新 digest）。
- **postgres/caddy 立即跟移新版 digest**：有修复版而不跟 = 违反 D14 精神（D14 管的是「有修复却不用」）；caddy 公网暴露、PG 存全部数据，风险权重最高。执行前出 D13 影响面评估（新构建 changelog、风险面、回退 = 旧 digest），跟移后 trivy 重扫确认可修高危清零。
- **镜像自带 4 个有修复版的包（msgpack/setuptools/urllib3 等）并入步 2**：Dockerfile 收尾清理——未被项目引用的 uninstall；确属传递依赖的进 lockfile 锁安全版。
- **核验标准升级**：依赖/镜像「无未修高危」以 trivy 层扫 + 漏洞库为准，release notes 核对仅作参考（步 1 教训）。

### 升级作业指导（长期有效，D13/D14 落地）

升级触发只有两种：**安全公告** / **明确的功能需要**。流程：

1. **影响面评估（必做，衡量后再升）**：谁依赖它（依赖树波及面）、changelog 有无破坏性变更、锁版本 diff、回退方案——输出评估结论再动手。
2. 分类处置：安全漏洞 → 等官方修复版，锁「最安全版本」；锁的版本本身被投毒 → **降级**回上一个安全版本（反向操作）；功能更新 → 攒到开发批次，不追新。
3. 五步走：开发分支装新版 → 全量测试（pytest + ruff）→ 真实路径验证 → commit 留档（写明 from→to + 原因）→ 旧版本号保留可回退。
4. 一次只动一个包；Docker 镜像升级锁 tag + digest，永不 `latest`。
5. 镜像 digest 刷新：同 tag 的 digest 前移**不自动跟移**；触发器 = 安全公告或每 3 个月评估一次，走 D13 影响面评估后才跟移。
6. 漏洞核验标准：以 trivy 层扫 + 漏洞库为准，release notes 仅参考；「全生态无修复可用」的漏洞不算违反 D14——出暴露面评估、接受残余风险、挂跟修触发器即可（D14 管的是「有修复却不用」）。

### 步 2：工程三小件

目标：网络容错基建，为步 3 网关重试打底。
