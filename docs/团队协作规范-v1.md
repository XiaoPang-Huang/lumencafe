# 流光咖啡馆团队协作规范与交付流程 v1

> 适用对象：项目 owner（两人）+ 参与本项目的 AI 助手。
> 规范优先级：**[AGENTS.md](../AGENTS.md) 设计强制规则 > 本文 > 其他文档**。

## 0. 角色与职责

| 角色 | 承担者 | 职责 |
|---|---|---|
| 产品负责人 | 用户本人 | 拍板产品决策、验收交付物、维护需求池优先级 |
| 产品经理（PM） | AI 助手扮演 | 澄清需求、写 PRD 增量、拆任务卡 |
| 架构师 | AI 助手扮演 | 技术方案评审、数据结构设计、把关契约文档一致性 |
| 工程师 | AI 助手扮演 | 编码、迁移、联调、自测 |
| QA | AI 助手扮演 | 按 DoD 验收、回归检查、挑错 |

一人团队 + AI 时，四个 AI 角色由同一会话承担，但**流程步骤一个不少**——自检要像"换了一个人的眼睛"来做。

## 1. 标准交付流程（八步）

```
① 需求提出 → ② 参考检索 → ③ 原型拍板 → ④ 文档同步
→ ⑤ 任务拆解 → ⑥ 开发实现 → ⑦ 评审验收 → ⑧ 合并沉淀
```

1. **需求提出**：owner 口述即可；PM 角色复述确认范围，含糊点当场提问。
2. **参考检索**：凡涉及界面/视觉/交互，必须先 WebSearch/WebFetch 业界成功案例（AGENTS.md §一 已列参考池），说得出"参考了谁、借鉴了什么"才动手。
3. **原型拍板**：前端变更一律先在 `prototype/v2/` 做静态原型给 owner 看。**原型未拍板，不动真实代码**。
4. **文档同步**：原型涉及产品决策 → 同步 `docs/PRD-v1.md`、`docs/架构设计-v1.md`、`docs/架构定稿-v1.md` 三份 + 各自修订记录；工程约定变更 → 同步 AGENTS.md。
5. **任务拆解**：架构设计 §7 任务列表为准，按 T 编号（T01、T02…）依赖排序；每任务一张任务卡：

   ```
   T0X｜标题
   目标：一句话说清交付什么
   验收：可勾选的 DoD 条目
   涉及文件：预计改动路径（见 docs/项目地图-v1.md）
   依赖：前置任务编号
   ```

6. **开发实现**：按 §2 工程规范编码；金额一律「分」；前端交互事件委托；迁移只加新文件。
7. **评审验收**：QA 角色按 §4 DoD 逐项核对；视觉类交付 owner 亲自过一遍。
8. **合并沉淀**：commit（原型阶段攒批等 owner 看完一起提）；更新 README/地图中受影响条目；写 `.workbuddy/memory/` 当日日志。

## 2. 工程规范

### 后端（backend/）
- 框架 FastAPI + SQLAlchemy + Alembic；lint 用 ruff（`backend/.venv/Scripts/ruff.exe`），测试 pytest。
- Alembic 迁移**只新增版本文件，不改历史迁移**；空初始迁移 0001 是链起点。
- 新配置项：`backend/app/config.py` 加字段 + `.env.example` 补注释 + README 环境说明。
- 新接口：在 `backend/app/routers/` 建模块，映射关系以架构设计 §4 为准，然后在 `app/main.py` 挂路由。

### 前端原型（prototype/v2/）
- 单页应用 hash 路由，`file://` 可直开；本地预览在 `prototype/` 起静态服务。
- 改 `main.css` / `app.js` 后必须 bump `index.html` 里的 `?v=` 版本号。
- 图标走 `data-ic` + `assets/js/icons.js` 注入，不手写散落的 SVG。

### 契约
- 三份 docs 文档 = 产品契约。代码与文档冲突时，**改代码前先改文档（经 owner 确认）**。
- 模型管理 = 纯网关、无应用绑定表、默认路由两标记——已定决策，勿在实现中"顺手改进"。

## 3. Git 规范

- 分支：小改动直接 `main`；跨多文件或实验性改动开 `feat/xxx`、`fix/xxx` 短分支。
- 提交前缀（小写）：

  ```
  feat(范围): 新功能     fix(范围): 修 bug
  docs(范围): 文档       style(范围): 样式/格式
  refactor(范围): 重构   chore(范围): 杂务
  ```

- 范围常用值：`prototype`、`backend`、`docs`、`admin`。
- 提交信息中文一句话，说清"做了什么、为什么"（原型阶段攒批提交时按主题拆多个 commit）。
- `main` 保持可运行：`docker compose up -d --build` 能起、health 能过。

## 4. Definition of Done（完成定义）

一个任务只有同时满足才标完成：

- [ ] 代码/原型按任务卡实现，自测通过（后端：相关 pytest 绿；前端：目标浏览器手过一遍）
- [ ] 涉及文档的改动已同步 + 修订记录已写
- [ ] 前端静态资源 `?v=` 已 bump
- [ ] ruff 无新增告警；无调试残留（print / console.log / 注释掉的死代码）
- [ ] 视觉类交付 owner 已看过并认可（援引了哪个业界参考能说清）
- [ ] `.workbuddy/memory/` 当日日志已追加

## 5. 反模式清单（踩过/禁止）

- ✗ 原型没拍板就写真实接口代码。
- ✗ 凭感觉设计界面（违反 AGENTS.md §一，一票否决）。
- ✗ 金额用元存库、前端展示层才换算。
- ✗ 手改数据库结构而不写迁移。
- ✗ 在三份契约文档之外另起"口头决策"——决策要么进文档修订记录，要么不算数。
