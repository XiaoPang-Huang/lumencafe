## 4. lockfile 机制说明（D6 落地）

```
requirements.in（人维护：直接依赖精确 == + 理由注释）
  └─ uv pip compile --universal --generate-hashes requirements.in \
       -o requirements.txt          # 机器生成：全量精确版本 + 每包 sha256
安装一律：pip install --require-hashes -r requirements.txt
开发全量：pip install --require-hashes -r requirements-dev.txt   # 主依赖+dev，一条命令装全
```

- 生成命令（uv 0.12.4，国内索引）：
  `uv pip compile --universal --generate-hashes --python .venv/Scripts/python.exe
  --index-url https://pypi.tuna.tsinghua.edu.cn/simple requirements.in -o requirements.txt`
  （dev 同理，源文件为 requirements-dev.in，其内 `-r requirements.in` 并入主依赖。）
- `--universal`：锁文件跨平台/跨 Python 小版本可用（含 linux/py3.14 的 Docker
  构建与 win/py3.13 本地开发两套 wheel 哈希）；`--require-hashes` 逐包校验。
- `backend/Dockerfile` 构建行已加 `--require-hashes`（哈希不符即构建失败）。
- 升级流程（D13）：先在本文件补影响面评估 → 改 `.in` → 重编译 → 干净 venv
  装通 → pytest + ruff + 冒烟 → commit 写明 from→to + 原因。
- 已知坑：Python 3.13.14 自带 pip 26.1.2 访问清华镜像有兼容问题
  （`from versions: none`），升级 pip ≥26.2.1 后正常；locktest 验收即用的 26.2.1。

## 5.1 步 2 digest 跟移核验（2026-10-25 trivy 实测，跟移裁定：不跟）

> 背景：v2.3 拍板「postgres/caddy 立即跟移新 digest」。步 2 执行前实测发现跟移前提不成立，需求会话裁定**本次不跟移**（修订拍板，见增量 v2 v2.4）。

| postgres:18-alpine | 77f58511…（PG 18.6 / Alpine 3.24.2） | 898c60cb…（PG 18.6 / Alpine 3.24.3，2026-10-21 构建） | HIGH/CRITICAL 检出**完全一致**：gosu 26 条（含 Critical CVE-2025-68121，docker-library 预编译二进制内嵌旧 Go stdlib）+ brotli-libs 1.2.0-r1 可修 CVE-2026-111497（修复版 1.2.1-r0 已在 Alpine 仓库但镜像构建未收编）。**跟移零安全收益** |
| caddy:2-alpine | d8542f48…（v2.11.7 / Alpine 3.23.6） | eb4d35b7…（仍是 v2.11.7 / Alpine 3.23.7，2026-10-21 构建） | 检出完全一致：caddy 二进制 5 条可修（内嵌 Go 1.26.8 stdlib）+ brotli-libs 可修。**跟移零安全收益** |

**裁定理由**：残留可修项均为上游烘焙二进制（gosu/caddy）与未收编的 Alpine brotli，容器内不存在可升级形态；D14 管的是「有修复却不用」，此处修复在镜像里**不存在**，不适用。与 v2.3 拍板的前提（跟移可清零）不同，故修订。

**跟修触发器（挂升级作业指导第 5 条）**：
1. docker-library 用新 Go 工具链重建 gosu / postgres 镜像收编 brotli 修复版；
2. caddy 发布 > v2.11.7 新版；
3. 每 3 个月例行评估时重扫对比。
任一触发 → 走 D13 影响面评估后跟移。

**残余风险接受**：gosu 26 条（容器内 postgres 以 root 启动后即降权，gosu 暴露面极小）+ caddy/brotli 共 6 条，记录在案。
