## #4 表单校验 → :user-valid/:user-invalid

**现状**：金额/分类校验走 toast 提示（app.js 记账提交分支）；改密码走 JS 手动判断。

**重新评估**：体检报告高估了收益。金额与分类是自定义控件（chips/seg 按钮组），`:user-valid` 只作用于原生表单元素，帮不上这两个主校验点；真正受益的只有金额 input 和改密码两个密码框，约占全部校验场景的 1/3。

**风险**：toast 提示是全局统一反馈，改成内联文案后，校验样式要与每个弹窗的字段布局单独对齐，回归点多于收益点。

**触发条件**：真前端（非原型）实现表单时，按「原生 input 用 :user-valid，自定义控件用 aria-invalid + 内联文案」的标准做法一步到位。

## #5 长列表 → content-visibility: auto

**现状**：文献列表一次渲染约 100 行；账目、会话列表同模式。

**重新评估**：100 行量级很小，首屏渲染不是瓶颈。加的收益主要是超长列表（500+ 行）的滚动流畅度。

**注意点**：必须配 `contain-intrinsic-size`，否则滚动条会跳动；它与「查找页面内容」、滚动锚定存在已知小冲突，需实测。

**触发条件**：真前端做虚拟列表/分页时一并考虑。原型阶段单独立项不值。

## #7 路由切换 → View Transitions API

**现状**：`render()` 用 `void view.offsetWidth` 重排 hack 重启动画（app.js 路由渲染处），CSS 注释自证 transform 残留影响 fixed 定位、移动端用负偏移硬补。

**重新评估**：这是四项里唯一有真实技术债属性的——两个 hack 确实丑。但：

- Baseline 属 Newly available（2025-10 起全支持），需特性检测降级（约 3 行），降级路径又回到现有 hack，等于维护两套。
- 切换后需手动迁移焦点、尊重 reduced-motion，指南要求一个不能少。
- 移动端快照捕获在低端机有实测成本。
- 原型阶段的页面切换动画当前工作正常，用户无感知痛点。

**触发条件**：真前端重写路由层时直接用 View Transitions 作为默认方案，hack 不进新代码。原型不再回填。

## #8 浮层点击外部收起 → Popover API

**现状**：模型选择器（app.js 模型弹层部分）与角色下拉各有一套手写「点外关闭」（click 委托 + closest 判断）。

**重新评估**：两套逻辑合计不到 20 行，已稳定运行。改 Popover API 需要：

- 给每个浮层加 `popover` 属性并改造触发按钮为 `popovertarget`；
- 保留旧逻辑作降级（体检报告自标 ⚠️），形成长期双份维护；
- 视觉零变化。

**结论**：不动。收益为零、维护成本翻倍。若未来浮层数量增长到 5 个以上再统一评估。

## 附：已否决项备忘（维持体检报告结论）
