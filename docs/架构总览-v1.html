01整体架构图

从下往上看是「建造顺序」，从上往下看是「一次请求的旅程」。带圈数字 ①–⑦ 是连线上标注的说明，对照图下方清单阅读。
  1. 1HTTPS / SSE —— 浏览器与服务器的加密通话；SSE 让服务器能持续「播报」进展（如 Agent 任务进度条），不用反复刷新。
  2. 2OpenAI 兼容 —— 接口格式与业界标准一致，第三方程序拿现成的工具就能接入，像电器用标准插头。
  3. 3reverse proxy（反向代理） —— 总前台：所有请求先进这里，再按规则转给内部对应部门。
  4. 4SQL :5432 —— 应用读写数据库的标准方式；5432 是 PostgreSQL 的默认门牌号。
  5. 5HTTP :8787 —— 应用向 AI 沙箱派任务的内部电话线，8787 是沙箱服务的内线号码，只在内部网络可达。
  6. 6pg_dump 每日 —— 每天把数据库完整导出一次，交给备份程序存档。
  7. 7模型出口 —— 沙箱里的 AI 想调模型只能走这一条路，便于统一计费和管控。

02逐层讲解 · 咖啡馆类比

把整套系统想象成一家咖啡馆：你是顾客，Caddy 是前台，api 是后厨，数据库是仓库，AI 沙箱是外包工作室。

L1 用户层 —— 谁在使用顾客

你在浏览器里使用对话、记账、文献、Agent 四个功能；外部程序也可以凭「钥匙」（token）直接调用模型接口。就像顾客进店点单，或打电话来订餐。

L2 接入层 · Caddy —— 前台唯一的门

所有流量只从一个门进来：看页面的请求发给前端文件，/api 开头的转给后厨，/admin/hatchet 转给排班室。前台不认识任何人，但谁都绕不开它；HTTPS 加密也是在这里完成的。

L3 应用层 · api —— 后厨 + 收银台系统的大脑

四个工位：业务路由是点菜窗口，按功能把单分给对应档口；服务层是厨师，真正干活——调模型、跑流水线、存文件；管理面是店长办公室，管用户、模型、钥匙；Hatchet worker是排班经理，到点或有活时派任务。底部蓝色横条是模型网关：全店唯一收银台，验钥匙、按用量记账、出事自动拉闸。

L4 数据与沙箱 —— 仓库 + 外包工作室存数据 & 关 AI

PostgreSQL 是仓库兼账本，所有数据只存这里。pi-runner 是外包 AI 的独立工作室：它干活时碰不到仓库，成果只能放到指定托盘（/output 卷），由后厨验收后才正式入库——这就是「沙箱」的意义。

L5 基础设施 —— 后勤与供应商兜底 & 外援

backup 每晚把账本完整复印一份存进保险柜（另一目录，防误删）。外部依赖是供应商：模型公司（DeepSeek 等）和文献数据库——店里不生产它们，只按需采购。

03Agent 任务时序图

以「下载 OA 论文」为例：从提交任务到 SSE 关闭的完整链路（已按真实验收路径核对）。
一句话看懂：你在弹窗里「下单」，后厨（api）登记后喊排班经理（Hatchet）派活，临时工（沙箱里的 AI）开始干活——每做一步都实时播报进度，最后把成果放上托盘、后厨验收入库。
sequenceDiagram autonumber actor U as 用户 participant FE as modal-agent 弹窗 participant API as api (FastAPI) participant H as Hatchet worker participant PR as pi-runner 沙箱 participant GW as /gw/v1 网关 participant LLM as 模型厂商 participant MCP as papers MCP participant VOL as /output 卷 U->>FE: 填写任务「下载 arXiv 1706.03762」 FE->>API: POST /agent/runs API->>API: INSERT pi_runs(pending) API->>H: push 事件 pi-run{run_id} API-->>FE: 202 {run_id} FE->>API: GET /agent/runs/:id/events (SSE) H->>PR: POST /api/runs PR-->>API: SSE session.subscribe API-->>FE: 逐帧转发工具事件 loop agent 多轮推理 PR->>GW: /chat/completions (stream + tools) GW->>LLM: 转发（注入 provider key） LLM-->>PR: tool_calls / 文本增量 end PR->>MCP: download_arxiv(1706.03762) MCP-->>PR: PDF 字节流 PR->>VOL: 写 result.md + PDF H->>PR: 轮询状态至终态 H->>API: 卷产物 → storage.put(pi/) H->>API: UPDATE pi_runs(completed) API-->>FE: run_end(completed) → 关闭 FE-->>U: 已入库 · 事件流定格
SSE 建立早于沙箱建 run 时，pi_client 会对 404 短重试（30s 窗口）。
每轮模型调用经网关落 llm_call_logs，pi-runner 专用 token 单独核算成本。
步骤 8–12 会循环多轮：AI「思考 → 调工具 → 看结果 → 再思考」，直到任务完成。

04容器拓扑图

docker-compose 六个容器、两张网：default 业务网与 sandbox 隔离网；api / caddy 双网桥接。
一句话看懂：六个「集装箱」分两个房间办公。业务房间（绿框）大家互通；AI 工作室（红框，pi-runner）在隔离房间，只能通过前台（caddy）对外联系——数据库根本不在它的房间，想碰也碰不到。
沙箱够不到 db：db 不在 sandbox 网，容器内实测 5432 不可达。
pi-runner 的模型出口只有一条：caddy → /gw/v1 → 专用最小权限 token。
hatchet 控制台不公网暴露，经 Caddy /admin/hatchet 子路径访问。

06多账号与数据归属图

圈子产品（设计容量 10~100 账号）下「谁能看见什么、数据归谁」：共享 schema + user_id 列 + 应用层过滤；所有业务表级联删除，删账号即带走全部个人数据。
一句话看懂：一张大账本，每行数据都写着主人的名字。左半边是「人」——账号、角色、权限；右半边是「数据」——15/16 业务表已带 user_id（删账号自动级联清空）；管理员独占底部一排出纳与钥匙；唯一要补的是蓝色那张费用流水表，加上 user_id 才能按人算账。
防漏过滤靠工程约定：service 层第一参强制 user_id、CI grep 扫描、每域一条越权测试（A 拿 B 的资源 id 必须 404）。
RLS 与库级隔离均否决：连接池共享 + 1-2 人团队，应用层已够；>500 用户再评估。
唯一约束维持「用户内唯一」；users.username 全局唯一（登录标识）。

07资源预算（2核4G / 70G）

设计容量 10~100 账号、实际负载轻度的口径测算（评审估算值）。PDF 与产物走 COS，不占本地盘。
一句话看懂：常态用掉不到一半内存，就算「早上抓取批 + 有人跑 Agent」撞车的最坏窗口也只到七成——余量充足，但 pi-runner 的 1G 封顶不能再上调。存储大头是系统与镜像，数据本身增长很慢。
扩容触发只看用户可感知时延：Agent 排队 P95 >10 分钟连续两周 → 先升 4c8g，再考虑 pi-runner 迁第二台 VPS。
存储侧待办：pi-output 卷 GC 策略、llm_call_logs 90 天明细清理（月汇总已设计）。

08应用操作时序

对话 / 记账 / 文献三个域「一次操作怎么流转」。Agent 域见 ③。

对话 · SSE 流式

sequenceDiagram autonumber actor U as 用户 participant FE as 对话界面 participant API as api (FastAPI) participant DB as PostgreSQL participant GW as /gw/v1 网关 participant LLM as 模型厂商 U->>FE: 输入消息 FE->>API: POST /chat/completions (stream) API->>DB: 载入会话上下文（仅本人会话） API->>GW: /chat/completions（会话级模型选择） GW->>LLM: 转发（注入 provider key） LLM-->>API: SSE 增量 token API-->>FE: 逐帧转发 + 写 llm_call_logs API->>DB: 落 user/assistant 两条消息 FE-->>U: 流式呈现

记账 · 事务写入

sequenceDiagram autonumber actor U as 用户 participant FE as 记账界面 participant API as api (FastAPI) participant DB as PostgreSQL U->>FE: 记一笔（金额/分类/日期） FE->>API: POST /money/transactions API->>API: 校验（金额以分存储、日期不越界） API->>DB: INSERT（单事务） API-->>FE: 201 成功 Note over FE,DB: AI 记一笔 = 同一端点；自然语言先经 LLM 结构化再入库

文献 · crawl → parse → 入库（定时流水线）

sequenceDiagram autonumber participant H as Hatchet（cron 7:30） participant API as api (FastAPI) participant SRC as 文献源 participant COS as 腾讯云 COS participant DB as PostgreSQL H->>API: 触发抓取轮次 API->>SRC: crawl 新论文（去重 uq(user_id,pmid)） API->>API: parse 流水线（错峰 + 并发上限，防抢核） API->>COS: PDF / 产物上传（不占本地盘） API->>DB: papers / 订阅关系入库 API-->>H: 轮次完成（crawl_runs 记录） Note over API: 订阅推送按用户应用设置触发
三条链路共同点：全部先经 Caddy 鉴权，user_id 只从登录态取、不信请求体。
文献流水线与 Agent 任务共享 2 核：parse 批避开用户活跃时段（资源防呆）。

09术语速查 · 非 IT 版

三张图里出现的专业词，全部用一句话解释。按图分组，按需查找。

图 1 · 架构图

SPA（单页应用）
整个网站只有一个网页，切换功能不刷新页面，体验像手机 App。
HTTPS
浏览器和服务器之间的加密通话，防止内容被窃听或篡改。
SSE
服务器主动持续「播报」的通道。Agent 任务的进度条就是靠它实时推到前端的。
OpenAI 兼容
接口格式与业界标准一致，第三方程序拿现成的客户端工具就能接入，像电器用标准插头。
token（令牌 / 钥匙）
一串密码，证明「你是谁、能用哪些功能」。沙箱里只发一把最小权限的钥匙——只能调白名单模型。
反向代理（reverse proxy）
总前台：接收所有请求，再按规则转给内部对应部门。对外只暴露它一个门。
端口（:80 等）
服务的门牌号。一台服务器上同时跑多个服务，靠门牌号区分谁接客。
IP 直连 / 自签
不配域名，直接用服务器 IP 访问；加密证书自己签发，浏览器会提示风险，但流量已经加密。
FastAPI
用 Python 写后端服务的框架。后端 = 跑在服务器上、响应请求的程序。
Alembic
数据库结构升级工具，相当于数据库的「更新补丁程序」，只新增不修改历史。
Hatchet / worker
任务调度器：到点（定时）或来活（事件）时派任务给 worker（干活的进程）执行。本项目里 worker 嵌在 api 进程内，不额外占容器。
模型网关 /gw/v1
所有 AI 调用的唯一出口兼收银台：验证钥匙 → 按规则选模型 → 记账 → 上游出故障时自动切断。
计费 · 熔断
计费 = 按 token（AI 用量的最小单位，约等于字数）记每笔账；熔断 = 模型服务出问题时自动拉闸，防止故障拖垮全站。
MCP
让 AI 使用外部工具的通用插口，如「查论文」「开浏览器」，本项目的两大 MCP 就是这两样。
SDK
开发工具包——别人封装好的功能，拿来即用。我们把 Pi 的 SDK 嵌进自己写的服务里。
沙箱（只读根）
AI 干活的隔离工作室：文件系统只允许读、成果只能写到指定托盘，防止它误伤或乱改系统文件。
pg_dump · restic
pg_dump 是数据库自带的「整库导出」工具；restic 是备份程序，把导出结果加密打包、保留历史版本。

图 3 · 时序图

事件（push）
部门之间「喊一嗓子」：把活丢给调度器就继续干别的，不站在原地等回复。
轮询
每隔几秒去问一次「好了没」，直到拿到最终结果。
入库
文件正式存进对象存储，同时在数据库记一笔账，以后可检索、可追溯。
多轮推理
AI 反复「思考 → 调工具 → 看结果 → 再思考」，直到把任务做完，不是一问一答就结束。

图 4 · 容器拓扑

容器（Docker）
把程序连同它的运行环境打包成标准「集装箱」：在哪台机器上跑都一模一样，互相隔离不干扰。
卷（volume）
容器之间共用的「共享文件夹」，容器删了数据还在。
网（network）
容器间的内部局域网。sandbox 是隔离网：只有 api、caddy、pi-runner 三个成员，数据库不在群里。
NAT 出公网
隔离网里的容器可以主动访问互联网（如下载论文），但外面的东西摸不进来。
prod 覆盖层
生产环境的附加配置，覆盖开发默认值——比如关掉数据库对外的门，只保留前台的三个门。

图 6–8 · 多账号 / 资源预算 / 应用时序

RBAC
角色权限体系：给角色打包权限，再把角色发给账号——比逐个账号单独设权限好维护。
级联删除（CASCADE）
删账号时自动带走它名下所有业务数据，物理清空、不可恢复。
用户内唯一
同一篇论文你可以收藏，别人也可以收藏；约束只保证「同一个人不重复」。
腾讯云 COS
对象存储：文件放云端不占服务器磁盘，按需取用、按量计费。
月汇总
费用流水太多时，每月轧一次总账进小表，明细定期清理，统计查询永远跑在小表上。
