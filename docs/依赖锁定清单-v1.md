## 3. 影响面评估（D13：衡量后再升）

### 3.1 starlette 0.46.2 → 1.3.1

- **依赖树波及面**：starlette 唯一上级为 fastapi 0.143.0，其约束
  `starlette>=0.46.0`（**无上限**，已读安装包 METADATA 确认）→ 1.3.1 满足，
  无需联动升 fastapi，无其他包依赖 starlette。
- **changelog 破坏性变更**（官方 release notes 0.46→1.3 全区间）：
  1.0 移除的是 **Starlette 层**旧装饰器 API（`@app.route` / `@app.middleware` /
  `on_startup` / `add_event_handler` 等）。已核查 `backend/app`：仅
  `app/main.py` 使用 `@app.middleware("http")`——该装饰器由 **FastAPI 0.143.0
  自实现**（`fastapi/applications.py:4747`，内部走 `add_middleware(BaseHTTPMiddleware)`），
  不依赖 Starlette 已移除 API； lifespan 已在用（`main.py:34`）；全仓无
  StaticFiles / FileResponse / Jinja2Templates / `@app.route` / `on_event` 用法；
  测试无 `client.stream()` 依赖。
- **锁版本 diff**：仅 starlette 0.46.2 → 1.3.1 一个包（传递依赖，requirements.in
  显式钉住）。
- **回退方案**：git 回退本次 commit（旧 requirements.txt 为 `==x.y.*` 通配符，
  不保留旧星等式锁）；或在 requirements.in 改回 `starlette==0.46.2` 重编译 +
  重装（**不建议**：回退即重新暴露 3 条 HIGH CVE）。
- **残余风险**：1.3.1 发布较新，与 D14「久经考验」存在张力；但 D14 同时要求
  「无未修高危 CVE」，而 1.3.1 是唯一满足项，故按最安全版本原则选它。
  已用干净 venv 全量 pytest（100 过）+ ruff + 真实启动冒烟对冲风险。

- **是什么**：Hatchet 官方 Python SDK（持久化工作流引擎客户端），论文域步 B 定时抓取

- **依赖树波及面**：纯新增，无既有包被升级；与现有依赖无版本冲突（pydantic 2.14.1 /

## 4. lockfile 机制说明（D6 落地）

```
requirements.in（人维护：直接依赖精确 == + 理由注释）
  └─ uv pip compile --universal --generate-hashes requirements.in \
       -o requirements.txt          # 机器生成：全量精确版本 + 每包 sha256
安装一律：pip install --require-hashes -r requirements.txt
开发全量：pip install --require-hashes -r requirements-dev.txt   # 主依赖+dev，一条命令装全
```

- 生成命令（uv 0.12.4，国内索引）：
  `uv pip compile --universal --generate-hashes --python .venv/Scripts/python.exe
  --index-url https://pypi.tuna.tsinghua.edu.cn/simple
  --override requirements-overrides.txt
  requirements.in -o requirements.txt`
  （dev 同理，源文件为 requirements-dev.in，其内 `-r requirements.in` 并入主依赖。
  `--override` 自步 D 起必填：cos-python-sdk-v5 陈旧元数据上限覆写，见 §3.5。）
- `--universal`：锁文件跨平台/跨 Python 小版本可用（含 linux/py3.14 的 Docker
  构建与 win/py3.13 本地开发两套 wheel 哈希）；`--require-hashes` 逐包校验。
- `backend/Dockerfile` 构建行已加 `--require-hashes`（哈希不符即构建失败）。
- 升级流程（D13）：先在本文件补影响面评估 → 改 `.in` → 重编译 → 干净 venv
  装通 → pytest + ruff + 冒烟 → commit 写明 from→to + 原因。
- 已知坑：Python 3.13.14 自带 pip 26.1.2 访问清华镜像有兼容问题
  （`from versions: none`），升级 pip ≥26.2.1 后正常；locktest 验收即用的 26.2.1。

## 5.3 步 4 备份镜像（2026-10-25，restic 0.19.1 多阶段构建 + D14 加固）

**为什么不能直接用 restic 官方镜像跑 pg_dump**（实测，2026-10-25）：
- restic 镜像基于 Alpine，`apk add postgresql-client` 只能装到 Alpine 分支默认的
  PG 客户端（3.20 分支 = PG16）；
- PG 客户端主版本必须 ≥ 服务器：`pg_dump 16.14` 对 PG 18.6 服务器直接
  `aborting because of server version mismatch`，dump 为空文件。

**构建形态**：`deploy/backup/Dockerfile` 多阶段——restic 官方镜像为底座，从本项目
**已锁 digest 的 postgres:18-alpine 镜像**（77f58511…，db 服务同款，同为 Alpine 3.24
分支 ABI 完全匹配）复制官方 pg_dump 18.6 二进制 + ldd 实测的 16 个依赖库
（libpq/libssl/libkrb5 等），版本随 digest 锁定，无浮动源（D6）。构建后 ldd 全解析、
pg_dump 18.6 对 PG 18.6 实跑通过。备份脚本（deploy/backup/backup.sh）走卷挂载
注入，改调度逻辑无需重建镜像。

**restic 版本选型（D14，三版本 trivy 实测对比）**：

| 版本 | 底座 | CRITICAL | HIGH | 可修面结论 |
|---|---|---|---|---|
| 0.17.3 | Alpine 3.20（已 EOL） | 4 | 72 | openssl 3.3.2 四条可修 CRIT（分支 EOL，容器内无可升级形态）+ Go 旧 stdlib/x-crypto 大量可修 HIGH（修复形态 = 新版 restic） |
| 0.18.1 | 同上代 | 4 | 72 | 与 0.17.3 同 |
| **0.19.1** | Alpine 3.24 | 3→**0**（加固后） | 32→**22**（加固后） | 可修面最小，取为底座 |

**D14 加固（Dockerfile 内，报告 trivy scan/step4-backup-0.2.0.json）**：

**加固后实测**：CRITICAL **0**；HIGH 22 全部为 restic 二进制内嵌 Go 模块

修复形态 = restic 用更新 Go 工具链重建，容器内不存在可升级形态，按 v2.4 先例
