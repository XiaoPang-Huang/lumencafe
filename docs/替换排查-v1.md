# 替换排查 v1（2026-10-25）

> 目的：把项目现有每一块过一遍——「这块能不能换成开源件？值不值得换？」
> 口径沿用《生态集成候选-v1.md》：库级随便复用；服务级克制（机器预算 1-2 个新容器）；平台级不碰。
> 判断口诀：**「我不会写/写不好的脏活」→ 外采值回票价；「我不想写的普通活」→ AI 写代码更快。**
> 许可证红线见该文档 §九.7：库级只收 MIT/Apache/BSD。

## 〇、结论先放

**现有自研没有一块是「必须换」的。** 2790 行服务层全是薄封装 + 领域逻辑，依赖面只有 12 个包（`backend/requirements.txt`），已经是「库级随便复用」的干净形态。

| 类别 | 数量 | 说明 |
|---|---|---|
| 现有自研 → 保留 | 全部 11 个模块 | 唯一可换可不换的是 papers_crawl 的解析 |
| 该补位（缺，不是替换） | 2 个 | restic 备份、Uptime Kuma 状态灯 |
| 建之前先外采 | 7 个 | 记忆/搜索/PDF/联网/MCP/通知/存储，见 §三 |
| 排查发现的问题 | 2 个 | APScheduler 未落地、LiteLLM 备胎降级（§四） |

## 一、现有自研模块逐个排查

依据：`backend/app/services/` 全部模块（wc -l 实测）+ `requirements.txt`。

| 现有部件 | 替换候选 | 结论 |
|---|---|---|
| chat_service.py（473 行，SSE 对话流） | 无同类开源（产品核心） | ✅ 保留。未来多步工具调用按既定走 LangGraph 库 |
| llm_gateway.py（194 行） | LiteLLM（库） | ✅ 保留，备胎**降级**。理由见 §四 |
| money_service.py（541 行，AI 记一笔） | 无（领域逻辑 + 提示词） | ✅ 保留 |
| papers_crawl.py（368 行） | feedparser（库·BSD）替手写 Atom 解析 | 🟡 可换可不换。arXiv 格式固定，`xml.etree` 手写解析能跑就别动；若日后接 RSS 种类多起来再换 |
| rate_limit.py（20 行） | slowapi（库） | ✅ 保留。20 行的活不值得为换而换 |
| rbac_service / route_service（82 行） | 无 | ✅ 保留，主权核心 |
| security.py（37 行）+ PyJWT/bcrypt | 已是库，仅薄封装 | ✅ 保留。第三方登录触发点见 §三 Casdoor |
| skill_library / skill_service / skillhub（809 行） | 无（Agent Skills 是开放标准） | ✅ 保留。Provider 插件点设计干净（`skillhub.py` 契约冻结），将来 skill 暴露成 MCP 工具用 FastMCP |
| seed.py（265 行） | 无（普通活） | ✅ 保留 |
| ORM 十六表 + Alembic | 无（平台主权） | ✅ 保留 |
| Postgres 18 + Caddy + docker-compose 三件套 | 已是开源件 | ✅ 维持，不折腾 |

小结：**没有一个模块是「自己造了不该造的轮子」。** 20 行以下的薄封装（rate_limit/security/rbac）换库反而多一层依赖。

## 二、该补位的（现在缺，不是替换）

- **restic 备份**（CLI·BSD）：现在没有任何备份容器/脚本。`pg_dump + restic` 异地一份。**用户数据上线前必配，优先级最高。**
- **Uptime Kuma**（服务·轻）：原型工作台的状态灯卡片目前是演示数据（`data.js`），它就是现成数据源；顺带把「服务活着没」管了。
- GlitchTip（服务·轻）：报错追踪，用户多了翻日志定位不过来那天再上。

## 四、排查发现的 2 个问题

1. **APScheduler 既定但未落地**。《生态集成候选》§一 定了「定时任务进程内 APScheduler」（v1.6 已同步契约文档），但 `backend/requirements.txt` 里没有 apscheduler，代码里也无 scheduler 痕迹——目前靠 `/internal/jobs/*` 手动触发顶着。落地时按既定装库即可，不用重开决策。
2. **LiteLLM 备胎降级**（修正上一轮判断）。读了 `llm_gateway.py` 实现：它不是全协议适配器，只是「OpenAI 兼容上游的统一出口」+ thinking 参数表驱动映射（DeepSeek/Qwen/GLM/Kimi 各家开关差异，docstring 前 14 行写明）。脏活本来就少，194 行自研是最薄方案；换 LiteLLM 会丢掉这层表驱动映射还得迁配置。**只有一种情况翻案：**要接非 OpenAI 兼容的原生协议（Anthropic 原生 / Bedrock）那天。

## 五、前端：最大的未来「替换」点（现在不动）

prototype/v2 是手写单页（app.js + main.css），为拍板服务，**不替换**。
但「真实前端立项」那天，手写 → **框架 + 组件库**是全项目最大的替换决策。方向建议：组件库选 Arco Design 体系（与设计参考火山方舟控制台同源，白底扁平风格已拍板），或其他同级（shadcn/Ant Design）——属库级随便用，届时按 AGENTS.md §一再对参考案例定稿。
