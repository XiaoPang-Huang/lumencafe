# 开发到部署流程 v1（2026-11-14）

> 本文档回答一个问题：**代码在我电脑上怎么跑起来，又怎么上到生产服务器。**
> 依据：`docs/白皮书-v3.md`（§02 环境基线、§14 升级纪律、§15 增补第 5 块）、`docs/开发步骤-v1.md`、`AGENTS.md`。
> 冲突处以白皮书为准；本文档发现的冲突列在 §7，拍板后修订。

---

## 1. 一张图看懂

```
本地（你的 PC）                      生产（2C4G Linux 服务器）
┌─────────────────────┐            ┌──────────────────────────┐
│ node src/server.mjs │  发版：    │ Caddy（HTTPS + 反代）     │
│ pi/chord/pg 驱动    │ git push → │   ↓ 反代                 │
│ 改代码即时生效       │ 服务器拉代码 │ 主程序（systemd 管）       │
│ PG 在本地 docker 容器│ npm ci →  │   ↓                      │
└─────────────────────┘ systemctl │ PG 容器（docker engine）   │
   日常开发只在这半边   │ restart  │ COS（备份、PDF 原件）       │
                                   └──────────────────────────┘
```

一句话：**日常开发全在宿主机（你的 PC）上；生产主程序用 systemd 直接跑 Node，不打镜像；只有发版时才推代码，服务器自己装依赖、跑迁移、重启。**

---

## 2. 本地开发（日常循环）

前提（一次性，环境基线见开发步骤 §0）：Node 24（`D:\nodejs`）、Docker Desktop、pg 容器、`.env` 已建好。

每次开发的固定动作：

```bash
docker start pg                    # 1. 起数据库（挂掉的容器才需要）
node src/server.mjs                # 2. 起主程序（开发热重用 npm run dev）
# 3. 控制台打印主人登录链接，浏览器打开即登录
# 4. 改代码 → 重启或热重载 → 验证
```

注意三点：

- **验 Node 版本**用 `D:\nodejs\node.exe -v`，PATH 里排前面的是 WorkBuddy 自带的 Node 22。
- **curl 测本地**必须加 `--noproxy "*"`，否则 Clash 代理会劫持回环地址请求。
- **数据库结构**改了只管写 `migrations/xxxx_xxx.sql`，主程序启动时自动跑未执行的；清库重建也是启动时一键恢复（0B 已实测）。

## 3. 依赖与升级纪律

新增依赖（升级同理）：

1. 版本**精确锁**（写死 `1.5.2` 这种，禁止 `latest`、慎用 `^`）；
2. `npm install` 后 `npm audit` 必须 0 漏洞；
3. lockfile（`package-lock.json`）随代码一起提交；
4. 生产装依赖一律 `npm ci`（照 lockfile 装，不解析新版本）。

升级任何包（含 pi / chord / Node 本体）走五步：**影响面评估 → 锁版本 → 全量测试 → 真实路径验证 → 生产同步升**。本地和生产用同一套版本基线（白皮书 §02 拍板），不允许「我这能跑」。

## 4. 提交与推送红线

- 每个任务完成（测试通过）**立即提交**，不攒批。格式：`feat(范围)/fix/docs/chore + 中文一句话`。
- **推送前必查**：`.env`、密钥、用户数据、`.data/`、`node_modules/` 不被跟踪（`.gitignore` 已覆盖，push 前 `git status` 过一眼）。
- 推 GitHub 前**先开 VPN**，且先查系统代理当前端口（Clash 端口会变），stale 会推失败。

## 5. 生产部署形态（按白皮书拍板）

服务器是一台 2C4G Linux，装裸 docker engine（版本对齐本地 Docker Desktop）。三件套：

| 组件 | 形态 | 说明 |
|---|---|---|
| Caddy | 直接跑 | HTTPS + 反向代理；纯 IP 访问，不用域名（2026-10-25 拍板沿用） |
| 主程序 | **systemd 服务** | Node 直接跑，代码在服务器上；**不打成镜像**（白皮书 §15-5） |
| PG | docker 容器 | `pgvector/pgvector:0.8.7-pg18-bookworm`，数据挂卷 |

> 主程序为什么不打镜像：就一套代码、两台机器规模，systemd 管 Node 足够简单；镜像的价值（环境一致）由「同一套版本基线 + lockfile + npm ci」保证。

生产 compose（Caddy + PG 的编排）在**第 0 批 0C 完成后**补到 `deploy/`（开发步骤 §4 遗留清单）。备份脚本（SQLite + PG 定时备份到 COS）是白皮书 §15-5 明确要求，不能停留在「有备份」一句话，落地时间列入 §7 待办。

## 6. 发版步骤

代码从本地到生产，按顺序：

1. 本地全量测试 + `npm audit` 0 漏洞；
2. commit + push（VPN + 查代理端口）；
3. 服务器 `git pull`；
4. 服务器 `npm ci`（依赖有变化时）；
5. `systemctl restart lumencafe`——**migration 随启动自动跑**，不用手工碰数据库；
6. 浏览器开生产地址验一遍登录页和关键路径。

回退 = `git checkout 上一个 tag/commit` + `npm ci` + 重启。依赖版本都在 lockfile 里，回退可复现。
