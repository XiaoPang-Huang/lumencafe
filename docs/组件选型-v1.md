# 第一部分 · 候选清单与触发点（原《生态集成候选 v1》，2026-10-24）

> 讨论定稿：三层复用模型 + 触发点清单。原则：**库级随便复用（自研的常规操作）；服务级按需克制（只接"脏活明显更值"的，机器预算 1-2 个新容器）；平台级不碰（产品主权永远在自有 FastAPI + Postgres）。**
> 判断口诀：组件解决的是「我不会写/写不好的脏活」（解析、协议适配）→ 外采值回票价；「我不想写的普通活」（入库、调度、通知）→ AI 写代码更快更省心。
> 机器约束：VPS 现有 db / api / caddy 三件套，新容器按个位数预算（轻量 50MB 级如 n8n→ntfy/Miniflux 随意；重量级 1-2G 如 RAGFlow/Dify 需腾退或升配）。

## 一、定时任务 / 胶水流程

| 候选 | 层 | 结论（2026-10-24 用户拍板） |
|------|-----|------|
| **APScheduler 进程内自研** | 库 | ✅ **当前路线**。定时任务收回后端进程（v1.6 / 修订6 已同步三份契约文档），/internal/jobs/* 保留手动触发口 |
| n8n / Dify / Windmill 等编排平台 | 服务 | ❌ n8n 已移除（维护 workflow 不便）；触发点：定时任务增至 5-10 个、或出现非工程人员要改流程 → 再评估（届时优先 Prefect 其次 Dify） |
| 云函数+定时触发 / GH Actions cron | 服务 | ❌ 代码活在项目外、要回连生产库，不优于进程内 |

## 二、知识库 / RAG

| 候选 | 层 | 触发点 |
|------|-----|--------|
| **pgvector 摘要级自研** | 库/扩展 | ✅ 基线：papers 表加 vector 列，抓取即嵌入，检索一条 SQL 接对话注入点 |

## 八、关于腾讯 Octop（TencentCloud/Octop，MIT，2026-07 开源）

自托管多用户多智能体 AI 助手平台，功能面是本项目的超集（专家/技能/知识库/子智能体/IM 网关/定时任务）。**不作为底座**（产品重叠 + 主权重叠 + 仅 3 个月大 API 不稳），但四个拆分模块可单独当"工人"评估：`octop-harness`（Agent runtime）/`octop-memory`（Memory）/`octop-gateway`（IM 桥，见上表）/`octop-browser`（CDP 自动化）。其"专家/技能/记忆/网关"的拆分模式验证了本项目同构决策的方向。逐组件深评见本文第二部分（2026-10-24，结论：四个都暂不引入，触发点保留）。

## 九、增补候选（2026-10-24 第二批，待拍板）

> 应「还有哪些开源组件/服务可用」追问增补；候选现状均已逐条核实。层级判定照旧三层模型 + 判断口诀。
> 许可证是本节新立的硬约束，见 9.7。

### 9.1 对话能力（离第一/二批功能最近）

- **SearXNG**（服务·轻：<256MB + Redis 30MB）：自托管元搜索，JSON API 免 key 免查询费，给对话挂「联网搜索」——对标 DeepSeek 界面的标配功能。
  - 脏活判定：搜索引擎聚合适配是脏活 → 外采值回票价。
  - 坑位：settings.yml 要开 `formats: [html, json]`（默认只有 HTML，API 一律 403）；私用要把限流器放宽；上游引擎可能封 IP，靠多引擎轮换兜底。
  - 触发点：对话要联网搜索那天。**本批最可能先用上的服务。**
- **FastMCP**（库·Apache-2.0，约 23k stars，Prefect 维护）：MCP server/client 框架。装饰器十行把我们的能力（记账查询、文献检索、网关管理）暴露成 MCP 工具；也能当客户端接外部 MCP。
  - 配套价值：第三方现成 MCP server（如 MinerU 自带的）可直接挂进我们的 MCP 注入点。
  - 坑位：版本跑得快（1.x → 4.x），必须锁版本；官方 `mcp` SDK 是依赖更小的备选（API 不通用）。
  - 触发点：Skill 中心 / MCP 注入点立项那天。**库级随便用。**
- **trafilatura**（库）：网页正文/元数据提取，收藏剪藏从 HTML 抠正文（备选 readability-lxml）。
  - 触发点：收藏功能动工。

### 9.2 文献解析（细化 §二「上全文 PDF」触发点）

- **优先路线：arXiv LaTeX 源码**（e-print 源码包）✅：arXiv 论文大多附 LaTeX 源码，直接解析比任何 PDF 解析器都准，零模型零 GPU。PDF 解析只留给无源码/非 arXiv 文档。届时首选这条。
- **Docling**（库·MIT，IBM）：PDF→版面/表格/阅读顺序结构化；模型小（258M）CPU 可跑；LangChain/LlamaIndex 集成成熟。公式识别弱于 MinerU。**MIT 许可证对本项目最干净。**
- **MinerU**（进程/服务级）：公式、复杂表格、中文排版最强（2026-08 十二维横评 11 项通过）；自带 MCP server。但重（模型缓存 20GB 级，最好 GPU）+ 许可证非纯 Apache（附加条款/AGPL 说法，用前读 LICENSE）→ **只做独立进程网络调用，不库级嵌入**。VPS 无 GPU，只能 CPU 慢速模式，真要上量需单独算力。
- **zhparser / pg_jieba**（PG 扩展·零容器）：中文词级全文检索（记账备注搜索等），补 pgvector 语义检索的空白。
  - 触发点：站内搜索要中文分词那天。

### 9.3 模型网关周边（网关已自研，只补不换）

- **LiteLLM**（库/代理·MIT）：140+ provider 的 API 差异适配，正是「各家接口不一致」这块脏活的外采答案。现在 llm_gateway 自研适配够用；provider 膨胀到十几家再回头看，优先 Python 库模式嵌入适配层，不换网关本体。
- **one-api / new-api**（服务）：不引入（主权重叠）。只抄设计——后台的「令牌额度 / 倍率计费 / 用量报表」是 gateway_tokens 额度功能的现成参考（one-api 已是 AGENTS.md 的渠道管理参考对象）。new-api 比 one-api 活跃但 AGPL。

### 9.4 账号与文件（触发点备着）

- **Casdoor 或 Logto**（服务）：微信扫码 / 第三方 OAuth 登录的协议脏活。触发点：开放注册或微信登录立项。现在 JWT 自研够用。
- **MinIO**（服务）：S3 对象存储。触发点：附件/文献原文/图片规模化，或多机部署。现在本地磁盘 + Caddy 够。

### 9.5 运维可靠性

- **restic**（CLI·BSD）：增量加密去重备份，`pg_dump + restic` 异地一份，比自研备份脚本稳。**用户数据上线前就该配——本批唯一「现在就值得」的。**
- **GlitchTip**（服务·轻）：Sentry 兼容错误追踪。触发点：用户多了翻日志定位不过来。
- **Beszel**（服务·轻）：服务器资源监控，工作台状态灯数据源；与 Uptime Kuma 互补（一个管服务活着没，一个管机器扛不扛得住）。
- **Langfuse**（服务·重）：LLM 调用追踪/成本/prompt 版本/评估。触发点：多用户计量或 prompt 迭代要实验对比。重量级（v3 需 ClickHouse 等），要腾机器预算才上。

### 9.6 明确不引入

- 完整 LLM 应用平台（Dify / FastGPT / LobeChat / Open WebUI）：平台级不碰，照旧只当 UI 参考。
- Agent 框架再横跳（AutoGen / CrewAI 等）：LangGraph 既定。
- Keycloak / Authelia：身份全家桶太重，家庭/小团队用不上。
- Grafana / Prometheus 全家桶：超机器预算，9.5 的轻量组合够用。
- Ollama 本地推理：VPS 无 GPU，不现实。

### 9.7 许可证红线（新规矩，建议同步 AGENTS.md）

本项目 LICENSE = MIT，引入时：
- **库级嵌入**（import 进 backend）只收 MIT / Apache-2.0 / BSD。
- **AGPL / 强传染组件**（new-api、MinerU 新版等）只做独立服务、纯网络调用，不嵌入不改码；引入前读 LICENSE 全文（MinerU 有附加条款）。

# 第二部分 · Octop 深评（原《Octop组件评估 v1》，2026-10-24）

> 调研对象：腾讯云 Octop（自托管多用户多 Agent AI 助手平台）+ 四个拆分组件（harness / memory / browser / gateway）。
> 衔接本文第一部分§八 的结论：「平台级不碰、四组件当工人单独评估」。本文是逐个的深评。
> 所有事实已对照各仓库 README 原文核实（见文末依据）。

## 〇、结论先放

| 组件 | 结论 |
|---|---|
| Octop 主项目 | ❌ 不碰当底座；设计可抄 |
| octop-harness | ⏸ 暂不引入；触发点到了先走既定 LangGraph 路线 |
| octop-memory | ⏸ 留在候选（与 Mem0 二选一实测）；有新判据 |
| octop-browser | ⏸ 暂不引入；真要浏览器自动化时它是首选 |
| octop-gateway | ⏸ 留在候选；双向 IM 那天直接上它 |

一句话：**现在一个都不用装**。但有 4 个新发现值得记进候选表（见 §三）。

## 一、Octop 是什么

腾讯云开源的「自托管多用户多 Agent AI 助手平台」，MIT 协议。

- 主项目 = 完整产品：Web 控制台、用户/权限、专家库、知识库、定时任务、IM 网关，功能面是本项目的超集。
- 四个组件单独开源、单独上 PyPI，官方明说「只拿你需要的那一块」。
- 成熟度：主项目 1.0.2b6（beta）；组件 1.0.x。2026 年 10 月刚开源，接口还会动。

## 二、逐个评估

### 1. Octop 主项目（平台级）→ 不碰

**优点**：开箱即用的控制面（用户、权限、额度、专家、知识库、IM）；一条命令部署；多用户记忆隔离。

**缺点 / 风险**：自带 Web 控制台和用户体系，和我们的 FastAPI + Postgres 产品主权直接冲突；两套账号两套权限；beta 版 API 不稳；上了它我们产品就没个性了。

**与本项目的适配与冲突**：功能重叠是全量重叠（对话/记账/文献/模型管理它都有对应物）。这与本文第一部分§八「产品重叠 + 主权重叠」的判断一致，维持原判。

**推荐**：❌ 不作为底座、不部署。但它的设计思路对我们有参考价值，见 §四。

### 2. octop-harness（Agent 运行时库）→ 暂不引入

**它是什么**：把 LangChain 团队的 deepagents 封装成可部署的 Agent 运行时。是库不是服务。图运行时用 LangGraph + SQLite checkpoint。

**优点**：
- 模型路由（ChatModelFactory）：OpenAI / Anthropic / Bedrock + 17 个国产预设，支持 OpenAI 兼容 base_url；
- 多 Agent 注册表 + Teams 互派活；工作区可换（本地 / S3 / COS / Postgres）；
- 安全护栏开箱：工具护栏、文件系统权限、PII 脱敏（内置大陆手机号 / 身份证识别清单）；
- LangGraph 派活栈和我们的首选路线（第一部分 §四）同源。

**缺点 / 风险**：
- 会把 deepagents / LangChain 整棵依赖树拉进后端，我们现在的 FastAPI 后端是很干净的轻依赖；
- 它自带模型路由，和我们「模型管理 = 纯网关」的主权决策是第二套路由（虽然它的 base_url 可以指向我们 `/gw/v1`，Key 仍留在网关，但模型注册表会重复一份）；
- 3 个月大，主项目还在 beta，接口变动是常态；
- 依赖树对 Python 3.14 的兼容未验证（我们 Dockerfile 用 `python:3.14-slim`，它标称 3.12+）。

**与本项目的适配与冲突**：我们的对话现在只是 SSE 单轮流（架构设计 §5.2），多步任务 / 工具调用的需求还没立项。冲突点主要是模型路由重叠（可用 base_url 指向网关缓解）和依赖树增重。

**推荐**：⏸ 暂不引入。触发点分两级——
- 对话要多步任务/工具调用 → 仍按既定路线先用 **LangGraph 库级**自己拼（轻、可控）；
- 需求升级到「多 Agent 互相派活 / 被 IDE 经 ACP 驱动 / 要开箱 PII 脱敏」→ 再评估 harness。

### 3. octop-memory（记忆库）→ 留在候选，与 Mem0 二选一

**它是什么**：Agent 长期记忆库，纯标准库 + SQLite/FTS5 起步（零核心依赖），可选 Postgres。是库（Python API / CLI / JSON-RPC），可进程内嵌。

**优点**：
- 分层蒸馏：原始事件 → 事实卡（AtomCard）→ 实体页，树状组织，召回按 token 预算裁剪；
- **零核心依赖**，进程内嵌符合我们「库级随便复用」的口诀，不加容器；
- 支持 PostgreSQL（独立 schema + namespace 隔离），和我们业务库可共存；
- **附赠 LangGraph checkpointer（SQLite/PG 可选）**——正好接我们 LangGraph 首选路线；
- 记忆可打包迁移（.hmpkg），「记忆是资产」。

**缺点 / 风险**：
- **向量搜索是 mock、默认关闭（README 原文承认 Chroma/Qdrant 集成未验证）**——主打词法检索（FTS5），和我们「pgvector 摘要级」基线是两条路线；
- 自动蒸馏要注入 LLMClient（可指向我们网关，但多一层接线）；
- 3.14 兼容未实测；数据落自己的 schema，和「业务数据进业务表」的直觉有摩擦。

**与本项目的适配与冲突**：本文第一部分§三 已定「Mem0 首选，octop-memory 小规模实测二选一」。本次核实给出二选一的新判据：

- 检索最终走向量（pgvector 统一检索）→ **Mem0** 更顺（可挂 pgvector）；
- 要零依赖、词法召回、顺带拿 LangGraph checkpoint → **octop-memory** 更顺。

**推荐**：⏸ 维持候选不动。触发点 = 对话需要跨会话个性化记忆（第二批之后）。届时实测比四件事：召回质量、和对话注入点的衔接成本、Python 3.14 兼容、Postgres 下与业务库共存表现。

### 4. octop-browser（浏览器自动化库）→ 暂不引入

**它是什么**：CDP 直连 Chromium 的浏览器自动化（运行时不依赖 Playwright），带 MCP server。

**优点**：元素 ref 定位稳（页面重排不点空）；轻量 DOM 输出省 token；登录态 profile 持久；录一遍回放（record & replay）；约 20 个 action 兼 CLI；自带 MCP server，任何支持 MCP 的 Agent 直接接。

**缺点 / 风险**：要拉 Chromium 二进制（几百 MB）；我们目前没有浏览器场景（arXiv 抓取走 HTTP API 就够，见第一部分 §六）。

**与本项目的适配与冲突**：当前无冲突也无需求。它的 MCP server 和我们未来的 MCP 注入点天然咬合，这是它最大的长期价值。

**推荐**：⏸ 暂不引入。触发点 = 出现「需要 JS 渲染 / 登录态」的采集、剪藏需求（届时对照 Karakeep 候选）、或给对话 Agent 开「操作网页」工具。到那天它是首选。

### 5. octop-gateway（IM 桥库）→ 留在候选

**它是什么**：10 个 IM 平台一套消息抽象（飞书 / 钉钉 / QQ / 企微 / 微信 iLink / 元宝 / 小艺 / MQTT / Telegram / Discord）。**是纯 asyncio 的库，跑在你自己的进程里**，不是独立服务。

**优点**：
- 写一个异步处理器，所有平台通用；token 流式输出（DELTA）是一等公民；
- 主动推送（push_text / push_to_all）也内置——单向通知场景它也能干；
- 限流 / 超时 / typing / 附件存储（MediaBackend）全内置；多租户隔离；群会话策略可配；
- 自定义平台继承 BaseChannel 即可复用整条管线；库级嵌入 = 不占机器预算的容器配额。

**缺点 / 风险**：长连接（WebSocket / 长轮询）跑在宿主进程里，和 FastAPI 同进程要自己管好生命周期（或单开一个小进程）；平台凭据申请是它省不掉的活；同样 3.12+ 标称、3.14 未实测。

**与本项目的适配与冲突**：本文第一部分§五 已列它为「双向 IM 时的候选」。本次核实的新信息是：它其实是**库**不是服务，比原表里「服务」的定级更轻，机器预算友好。无主权重叠（它只管消息通道，Agent 逻辑仍是我们的）。

**推荐**：⏸ 维持候选。触发点 = 需要双向 IM（在 IM 里发指令给助手）。届时直接上它，省掉逐平台写 webhook。若只是单向推送（论文更新提醒），ntfy 仍然最轻；但若迟早要双向，可以跳过 ntfy 直接攒到 gateway。

## 三、相对既有候选表的 4 个新发现

1. **octop-memory 附赠 LangGraph checkpointer（SQLite/PG）**——和我们 LangGraph 首选路线咬合，是它相对 Mem0 的加分项。
2. **octop-memory 向量搜索确认是 mock / 默认关闭**（README 原文）——「和 Mem0 二选一」的判据由此明确：走向量选 Mem0，走词法选它。
3. **octop-gateway 是进程内库而非独立服务**——按三层复用模型它更靠近「库级」，机器预算比原估计友好。
4. **harness 的模型路由支持 OpenAI 兼容 base_url**——将来若用它，模型 Key 仍可全部留在我们网关，「路由重叠」的冲突是可控的。

## 四、可借鉴的设计（不装代码，抄思路）

# 第四部分 · 网关与调度开源详评（2026-10-25，应「找业界最佳实现」调研）

> 结论先行：**不整体引入任何网关/调度服务**，采用「自研薄层 + 逐家抄设计」路线。理由与可抄清单见 §二；七个项目详解见 §一。调研信息均 2026-10-25 核实。

## 一、项目详解

### 1. LiteLLM（BerriAI/litellm，Python，MIT，~18k 星）

**是什么**：Python 生态最流行的 LLM 接入层，两种形态：① SDK 库（`litellm.acompletion()`，100+ 厂商统一成 OpenAI 格式）；② Proxy 代理服务（独立进程，带管理界面）。
**功能全景**：统一 API、路由策略（延迟/成本优先）、fallback 链、按虚拟 key 的预算与速率限制、花费日志（按 key/项目/模型）、缓存、guardrails 钩子、mock 响应（测试用）。
**长处**：覆盖面最大、文档全、Python 原生、SDK 形态零基础设施。
**短板**：① 2026-03 发生过 PyPI 供应链事件（使用必须锁版本）；② release 频繁、上游厂商怪癖偶有渗漏；③ 企业功能（SSO/审计）在付费云版。
**与本项目关系**：设计上的头号参照（虚拟 key ≈ 我们的 app_key）；SDK 形态可作为自研引擎的底座候选，见 §二。

### 2. one-api（songquanpeng/one-api，Go，MIT，~2 万星）

**是什么**：Go 写的 AI API 聚合网关，中文社区事实标准。
**功能全景**：多渠道管理（厂商×套餐平级，与本项目 Provider 模型同构）、令牌体系（分组/额度/过期）、按令牌的用量与额度统计、用户额度、兑换码、丰富的重试与渠道优先级。
**长处**：部署一个二进制、极轻；管理界面成熟；统计页签（数据/日志）可直接当 UI 参照。
**短板**：路由策略较简单；项目维护节奏放缓，活跃开发在分支 new-api。
**与本项目关系**：**界面 IA 的参照**（渠道/令牌/额度/日志四页签）；其「渠道」概念与我们 Provider 表几乎一一对应，说明数据模型没跑偏。

### 3. new-api（QuantumNous/new-api，Go，**AGPL-3.0**，~7k 星）

**是什么**：one-api 的活跃分支，功能超集。
**功能全景**：在 one-api 基础上加：渠道自动重试与优先级、按次/按 token 双计费、Midjourney 等绘图渠道、更细的日志与数据分析页。
**长处**：迭代快、功能全、UI 现代。
**短板**：**AGPL-3.0**——本项目 MIT，仅可作独立服务网络调用，不可嵌入/改写进代码；Go 技术栈与团队 Python 主栈不合。
**与本项目关系**：只当**功能清单参照**（看它还做了什么），不当代码或服务来源。

### 4. Portkey Gateway（portkey-ai/gateway，TypeScript，MIT，2026-03 起开源）

**是什么**：原商业 AI 网关，2026 年 3 月开源核心网关（ edge 运行时形态）。
**功能全景**：config 对象集中管理路由策略（fallback / load-balance / canary）、**熔断与断路器**（目标连续失败自动摘除、恢复自动切回）、请求/响应 guardrails、可观测性（日志侧，仪表盘在付费侧）、MCP 工具治理。
**长处**：把「生产级可靠性控制」做成了配置而非代码；熔断语义现成可抄。
**短板**：Node/edge 技术栈；社区版日志仪表盘弱（存储与面板是付费部分）。
**与本项目关系**：**熔断设计的首选参照**——比我们最初的「按顺序兜底」更进一步，建议抄（主模型连挂 N 次自动停用，备用顶上，恢复自动切回）。

### 5. Langfuse（langfuse/langfuse，MIT，~22k 星）

**是什么**：开源 LLM 可观测性平台（追踪/成本/评估/提示词管理一体）。
**功能全景**：每次调用一条 trace（含 token 明细与延迟）、**费用模型 = usage × 模型单价表**（单价可自维护、支持阶梯价）、按用户/模型/标签的仪表盘与告警、提示词版本管理、数据集与评估。
**长处**：费用与追踪的数据模型是业界标杆；MIT 全功能开源。
**短板**：v3 起自托管需 ClickHouse + Redis + Postgres + 对象存储，约 3 个额外容器——超出本项目容器预算。
**与本项目关系**：**费用统计的数据结构照它抄**（记账表 + 单价表 + 聚合查询），不部署它。

### 6. Prefect（PrefectHQ/prefect，Python，Apache-2.0，~24k 星）

**是什么**：Python 工作流编排平台（2026-07 收购 Dagster 后社区更大）。
**功能全景**：普通 Python 函数加 `@flow`/`@task` 即成流水线；调度（cron/间隔）、重试、缓存、崩溃恢复为引擎内建；自带 Web 控制台（运行历史、状态、定时规则全可视化）；自托管 Server + Worker 形态，Postgres 存储。
**免费吗**：核心框架 Apache-2.0、自托管**完全免费**；付费的只是官方云服务（多租户/RBAC/SSO 等企业功能）。
**长处**：装饰器心智负担最小；控制台现成；社区最大。
**短板**：至少 1 个常驻容器（Server）+约 1GB 内存；任务内崩溃从步骤头重试（无断点续跑）；非 Python 不支持。
**与本项目关系**：流水线组件的**成熟派选项**，见 §三。

### 7. Hatchet（hatchet-dev/hatchet，引擎 Go + Python/TS/Go SDK，MIT，~8k 星）

**是什么**：持久化工作流引擎 + 分布式任务队列。
**功能全景**：**Postgres 是唯二必需的存储**（RabbitMQ 仅高吞吐可选）——不需要 Redis/Kafka；durable execution（崩溃从断点恢复）；自带 UI（运行/定时/重试）；并发控制、速率限制、工作流间依赖。
**免费吗**：MIT 全仓库、无企业版目录、自托管免费。
**长处**：基础设施贴合度全场最高（复用现有 Postgres）；崩溃恢复语义优于 Prefect。
**短板**：项目较年轻（生产履历短于 Prefect/Temporal）；社区较小。
**与本项目关系**：流水线组件的**轻量派选项**，见 §三。

## 二、「能不能直接用 LiteLLM」——三条路径对比

**问题**：能不能直接用 LiteLLM，在它基础上实现其他开源项目的功能（熔断、统计、预算）？

| 路径 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 当库用（推荐） | `litellm` SDK 进 requirements；`Router` 类自带 fallback/冷却/重试；我们的 DB 配置层、app_key 记账、熔断抄 Portkey、费用抄 Langfuse，包在它外面 | 零新容器；厂商怪癖归它管；我们的模型管理界面照旧 | 替换 llm_gateway 的 httpx 调用层（mock/thinking 映射需对照验证）；锁版本防供应链风险 |
| B. 当服务用 | 部署 LiteLLM Proxy 容器，我们的 FastAPI 变纯客户端 | 预算/虚拟 key/花费日志/UI 开箱即用 | +1 容器与运维面；模型管理数据双份（要同步）；mock/thinking 定制要绕；供应链事件风险更大 |
| C. 不用，只抄设计 | 维持自研 194 行引擎，按 Part 四 §一 抄各家设计 | 零依赖增量；控制力最强 | fallback/熔断/预算全部自己写（约几百行 + 测试） |

**推荐路径 A**：理由是「库级随便用」与「服务级克制」的分界线——LiteLLM 以库形态进来不违反容器预算，还正好替掉我们迟早要补的厂商差异层；其他家功能（熔断、费用模型、UI）按设计参照逐件自研，不做服务集成。

## 三、Prefect vs Hatchet：调度组件结论

- **现在（≤5 条流水线）**：都不装。APScheduler + 自建 scheduled_jobs 表 + 后台页（零新容器，见《论文域组件参考与优化》§八.5）。
- **将来升级**：选 **Hatchet**。理由：唯一必需的存储是 Postgres（与现有基础设施完全同构，不添 Redis/Kafka）；MIT 无企业版分叉；崩溃断点恢复优于 Prefect。Prefect 是社区最大的稳妥备选（Apache-2.0 同样免费），若更看重生态与资料量可选它。
- 两家都免费（开源核心自托管免费，付费的是云服务/企业功能），许可证均无忧。
